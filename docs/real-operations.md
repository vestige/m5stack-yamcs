<a id="bus-payload"></a>

## 1. 衛星はバスとペイロードでできている

| 部分 | 役割 | M5Sat では |
| --- | --- | --- |
| バス | 衛星を動かすための共通部分。電源、通信、姿勢、計算機、熱など | M5Stack 本体。モード管理、HK、コマンド処理（`/M5Sat/Bus`） |
| ペイロード | ミッションのための機器。カメラ、センサー、通信機など | GPS ユニット（`/M5Sat/GNSS`） |

バスは「ペイロードを働かせるための土台」です。ペイロードに異常があっても、バスは動き続けて地上と通信できるように作ります。M5Sat でも、GPS ユニットを外しても HK は届き続けます。

---

<a id="modes"></a>

## 2. 運用モードと SAFE モード

運用モードは、衛星全体の動作の状態です。ペイロードはその中の1つの機器なので、「衛星全体のモードに合わせて、ペイロードの電源をどうするか」が決まります。

| モード | 本物の衛星での意味 | M5Sat では |
| --- | --- | --- |
| SAFE | 異常のときに逃げ込む、最も守りの固い状態。電力を食う機器を止め、地上と通信して原因を調べられる状態だけを保つ | ペイロードを切る |
| NOMINAL | 通常の運用 | HK と GNSS テレメトリを送る |
| MISSION | ペイロードでミッションを行う | 観測データを送る |

モードの**ルールと動き**（SAFE ならペイロードを切る、など）は衛星の搭載ソフトウェアが持ちます。地上と通信できない間も、衛星は自分で判断して動かないといけないからです。YAMCS の Mission Database は、衛星から届いた値の読み方と、コマンドの組み立て方を定めた「辞書」にあたります。

<a id="fdir"></a>

## 3. FDIR（異常時の自動退避）

FDIR（Fault Detection, Isolation and Recovery）は、衛星が異常を自分で検知し、影響を閉じ込め、安全な状態で動き続けるための仕組みです。宇宙機の設計でよく使われる言葉です。

**なぜ宇宙で特に重視されるか**

| 宇宙機の事情 | だから必要になること |
| --- | --- |
| 打ち上げたら、人が行って直せない | 壊れた機器を切り離して、残りで動き続ける |
| 地上と通信できる時間が限られている（低軌道の衛星なら、1回のパスは十数分） | 地上が気づくのを待たず、衛星が自分で安全な状態に逃げる |
| 遠くの探査機は、電波の往復に何十分もかかる | その場で判断する自律性が要る |

宇宙機では、機器・サブシステム・衛星全体と段階を分けて、「どの異常を、どの段階で、どう処理するか」を設計の早いうちから決めます。最後の砦が SAFE モードです。

**ほかの分野の似た仕組み**

| 分野 | 似た仕組み |
| --- | --- |
| 自動車 | 故障を検知すると、出力を落として走り続ける「リンプホームモード」 |
| 航空機 | 計器やコンピュータを多重にしておき、壊れた系統を切り離す |
| 工場の機械 | 異常を検知すると、安全側で止まる「フェイルセーフ」 |
| Web システム | ヘルスチェックで異常を見つけて、自動で再起動・切り替える（フェイルオーバー、サーキットブレーカー） |

**FDIR を止められるようにする理由**

わざと機器を抜き差しする試験のときや、FDIR の判断の条件そのものが厳しすぎるときに、地上の判断で一時的に止めます（M5Sat の `SET_FDIR`）。止めた守りは、終わったら必ず戻します。

**機器の立ち上がりを待つ**

機器の電源を入れてから動き出すまでには時間がかかります。M5Sat でも、ペイロードの電源を入れてから最初のデータが届くまでは長め（30秒）に待ち、一度動き出したあとは短め（10秒）で判断します。

<a id="two-layers"></a>

## 4. 二重の守り（衛星側と地上側）

| 守り | 役割 | M5Sat では |
| --- | --- | --- |
| 衛星側のルール | 何が届いても自分を守る、最後の砦 | 範囲外の引数、今の状態で実行できないコマンドを拒否する（`Satellite.cpp`） |
| 地上側のルール | そもそも危ないコマンドを送らない | 引数の範囲、送信の前提条件（Transmission Constraint）、重要度と承認フロー（Mission Database と `command-queue.yaml`） |

地上側のルールは、届いている最新のテレメトリで判断します。コマンドの結果がテレメトリに出るのを確かめてから次へ進む、というのは本物の運用でも基本です。

<a id="roles"></a>

## 5. コマンドの承認と役割分担

本物の衛星運用では、衛星に関わる組織が役割を分けています。

```text
ペイロード運用チーム ──観測の依頼──▶ 管制局（運用センター） ──コマンド──▶ 地上局（アンテナ） ~~~▶ 衛星
（科学者・利用者）                  ・コマンド担当が準備             （回線を提供する）
                                    ・責任者が承認して送信
```

| 役割 | すること | 承認との関係 |
| --- | --- | --- |
| 管制局（運用センター） | 衛星全体の運用に責任を持つ。コマンドの最終判断をする | YAMCS の待ち行列での承認は、ここでの「コマンド担当が準備 → 責任者（フライトディレクターなど）が確認して送る」という二人確認にあたる |
| ペイロード運用チーム | 観測したいことを決め、管制局に観測を依頼する | 依頼は計画（Timeline）として管制局に渡すことが多い。管制局は衛星の状態や電力などを見て、受けるかを判断する |
| 地上局（アンテナの局） | 衛星との回線を提供する。パスの時間にアンテナを向ける | 普通はコマンドの中身は承認しない。M5Sat では受信スクリプトと地上局の無線機（M5StickC）にあたる |

今の M5Sat はログインなし（全員が `guest`）で動かしています。YAMCS でユーザーを作ると、役割ごとに権限を分けられます。

- **Clearances**：運用者ごとに、送ってよいコマンドの重要度の上限を決める（例：ペイロード運用者は vital まで、責任者は critical まで）
- **待ち行列の担当**：待ち行列ごとに、使えるユーザーやグループを決める（`command-queue.yaml` の `users` / `groups`）

<a id="alarms"></a>

## 6. アラームの確認

| 操作 | 意味 | 運用での使い方 |
| --- | --- | --- |
| Acknowledge | 「見ました、対応します」 | 複数の運用者で見ているとき、「誰かが見ているだろう」で見落とすのを防ぐ。誰がいつ確認したかが残るので、気づくまでの時間を振り返れる |
| Shelve | 「わかっているので、しばらく通知しないで」 | 試験中など、鳴るとわかっているときに使う。戻し忘れると本当の異常を見逃すので、期限を付け、誰がなぜ止めたかを残す |
| Clear | 運用者が手で「終わったことにする」 | 値が正常に戻ったかを判断できないアラームを閉じたいときなど |

YAMCS は、一度鳴ったアラームを、正常に戻っても誰かが確認するまで一覧に残します。運用者が見ていない間に一瞬だけ起きた異常を、見落とさないためです。

**鳴らなくてよいときは鳴らさない（状態に応じたアラーム）**

アラームは、多すぎても役に立ちません。当たり前のことで何度も鳴ると、運用者は確認を流すようになり、本当の異常を見落とします（「オオカミ少年」になる）。そのため本物の運用では、機器の状態によって「正常の範囲」を変えます。たとえば、機器の電源を入れた直後の立ち上がり中や、試験のための特別な運用中は、普段なら異常とみなす値でも警報を出しません。

M5Sat では、ペイロードの電源を入れてから30秒（立ち上がり中）は、GNSS の「測位できていない」「衛星が4機未満」のアラームを出しません。衛星が HK で「ペイロードの電源を入れてからの秒数」（`PayloadOnTime`）を送り、YAMCS の条件付きのアラーム（XTCE の ContextAlarm）で、30秒以上のときだけ判定します。30秒を過ぎても測位できなければ、今までどおり警報が出ます。

<a id="planning"></a>

## 7. 時刻指定の運用と観測の計画

地球観測衛星などでは、観測を次のように運用します。

```text
利用者の依頼 → ミッション計画 → コマンドの予定表を作る → パスで送る → 衛星が予定どおり実行
                                                                      ↓
              データの処理・配布 ← 次のパスで地上へ送る ← 衛星のメモリに記録
```

| 段階 | 本物の運用 | M5Sat では |
| --- | --- | --- |
| 依頼 | 利用者（研究者や企業など）が「この場所を、この日時に観測したい」と依頼する | — |
| 計画 | 計画の担当が、依頼をまとめて観測の予定を作る。衛星の通り道、電力、熱、記録できる容量、地上局と通信できる時間などの制約を全部考える | 運用者が開始時刻と長さを決める |
| 予定表を作る | 1日分などの観測を、時刻つきのコマンドの列にする。1回の観測でも「機器を温める → 姿勢を変える → 観測する → 戻す」のように、たくさんのコマンドになる | `SCHEDULE_OBSERVATION` 1つ |
| 送る | 通信できるパスの間に、予定表をまとめて衛星へ送る。数時間〜数日先の分まで送っておく | Queues で承認して送る |
| 実行 | 衛星は、地上と通信できなくても、機上時刻を見て予定表どおりに自分で実行する。予定表の中身や進み具合はテレメトリで報告する | 機上時刻を見て MISSION に移り、終わったら戻る |
| 記録と送信 | 観測データは衛星のメモリに記録しておき、次のパス（大容量の回線や、別の地上局）でまとめて地上へ送る | 今はリアルタイムで送っている |
| 振り返り | 予定どおり観測できたか、計画と実際を比べる | 5-9（Timeline）でやる予定 |

ESA の宇宙機の標準（PUS）では、「時刻つきのコマンドを衛星の中の予定表に入れておき、時刻になったら実行する」仕組みが、決まったサービスとして定められています。M5Sat の `SCHEDULE_OBSERVATION` は、それを1件だけに簡単にしたものです。

**M5Sat で、より本物に近づけるなら**

- 観測1件だけでなく、時刻つきのコマンドを何件も予約できる予定表にする
- 観測データを衛星のメモリに記録しておき、次のパスでまとめて送る（README の「発展」）
- Timeline に予定を書き、Archive のデータと比べる（5-9）

<a id="onboard-time"></a>

## 8. 機上時刻

時刻指定のコマンドを実行するには、衛星が今の時刻を知っている必要があります。

| 方法 | 内容 |
| --- | --- |
| GPS で合わせる | GPS 受信機を積んでいる衛星は、GPS の時刻で合わせる。M5Sat はこの方法 |
| 地上から合わせる | 地上から時刻を送って合わせたり、衛星の時計と地上の時計のずれを測って補正したりする |

M5Sat では、GPS の時刻が届くたびに合わせ、その間は衛星の中の時計で数え続けます（`OnboardClock`）。ペイロード（GPS ユニット）を切っても時刻はわかります。まだ一度も合わせていなければ、時刻指定のコマンドは受け付けません。

## 9. 運用手順書

本物の衛星運用では、決まった作業の手順を、事前に書いて確かめておきます。M5Sat のコマンドスタックは、この運用手順書にあたります。

| 段階 | すること |
| --- | --- |
| 作る | 衛星の設計者と運用者が、作業ごとに手順を書く。「何を送るか」だけでなく、「各コマンドのあと、何を確かめてから次へ進むか」まで書く |
| 確かめる | シミュレータや地上試験で、手順どおりに動くかを確かめておく |
| 承認する | 確かめた手順を、運用で使ってよい手順として登録する |
| 使う | パスの間に、手順書を1行ずつ進める。決まった手順から外れる操作は、原則しない |
| 記録する | 実行した記録が残るので、何が起きたかを後で振り返れる |

**なぜ手順書にするのか**

- **パスの時間が短い**：十数分のパスの間に、その場でコマンドを考えていては間に合わない。手順が決まっていれば、迷わず進められる
- **間違いを減らす**：順番の間違いや、確認の飛ばし（コマンドの結果がテレメトリに出る前に次を送る、など）を防げる
- **誰がやっても同じ結果になる**：担当者が交代しても、同じ手順で同じように運用できる
- **異常のときこそ役に立つ**：慌てやすい場面ほど、事前に確かめた手順に従うことが大切。「SAFEからの復旧」のような異常時の手順は、本物の運用でも特に重要

<a id="training"></a>

## 10. 運用の訓練とシミュレータ

本物の衛星運用では、打ち上げ前に運用チームが何度も訓練（運用リハーサル、シミュレーション訓練）をします。打ち上げ後も、新しく入った運用者のために続けます。M5Sat の 5-10 は、この訓練にあたります。

| 訓練で確かめること | 理由 |
| --- | --- |
| 運用者が異常に気づけるか | 異常は予告なく起きる。打ち上げ直後の数日は特に危ない |
| 手順書が正しいか | 手順書の間違いは、訓練で使って初めて見つかることが多い |
| 判断の練習 | 「すぐ戻すか、原因を確かめるまで待つか」のような判断は、手順書だけでは身につかない |
| 役割分担と連絡 | 誰が気づき、誰が判断し、誰が承認するか |

**異常は、衛星ではなくシミュレータに入れる**

本物の訓練では、運用者は地上のシミュレータ（衛星の動きを真似るソフト）や試験用の衛星（エンジニアリングモデル）に向かって運用し、訓練の担当者がそこに異常を入れます。打ち上げる衛星のソフトには、秘密の指示で異常を起こす口は入れません。誤って宇宙で動くと危ないからです。

M5Sat には別のシミュレータがないので、衛星（M5Stack）がシミュレータの役も兼ねています。訓練用の指示（APID 111）は、運用者の使う YAMCS を通らない経路で届き、Command history にも Events にも出ません。運用者に見えるのは、本物の異常と同じ「症状」だけです。

**訓練の題材は、起こりうる故障から選ぶ**

本物では、衛星の設計のときに「どの部品がどう壊れると、何が起きるか」を洗い出しておき（FMEA など）、その中から訓練の題材を選びます。M5Sat の3つの出題も、本物でよく起きる異常に対応しています。

| M5Sat の出題 | 本物の衛星で起きること | 衛星の備え |
| --- | --- | --- |
| GNSS 受信の停止 | 機器の故障、ケーブルや電源の不具合 | FDIR が切り離して SAFE へ逃げる |
| コマンドの無視 | 受信機の故障、ソフトの不具合でコマンドを処理できなくなる | **コマンドロスタイマ**：決まった時間（数時間〜数日）コマンドが届かなければ、衛星が自分で受信機やコンピュータをリセットする。M5Sat には無い |
| 予告なしの再起動 | 放射線によるビット反転（シングルイベント）、ソフトの不具合でウォッチドッグがリセットする | 再起動の回数と理由を HK に出す。大事な設定は不揮発メモリに置く |

コマンドの無視は、アラームが出ないので、いちばん気づきにくい異常です。テレメトリは届くのにコマンドだけ通らないとき、地上の設備（地上局の送信機）を疑うのか、衛星の受信側を疑うのか、切り分けが要ります。

**振り返り**

訓練のあとは、時系列（いつ何が起き、いつ気づき、何をしたか）を見ながら振り返り、手順書や運用画面を直します。M5Sat では `tools/training_report.py` が、YAMCS に残った記録から時系列の表を作ります。アラームを確認するときのメッセージに推定した原因を書いておくと、あとで判断の筋道を追えます。

<a id="displays"></a>

## 11. 運用画面とトレンドの監視

本物の管制室では、衛星の状態を見る画面を目的ごとに分けています。M5Sat の運用画面（YAMCS の Displays）は前者、Grafana（[issue #21](https://github.com/vestige/m5stack-yamcs/issues/21)）は後者にあたります。

| | 運用画面 | トレンドの監視 |
| --- | --- | --- |
| 答える問い | いま衛星はどんな状態か。次のコマンドを送ってよいか | 何時間・何日にわたって、衛星がどう変わってきたか |
| 使う人 | パス中の運用者 | 衛星の設計者や解析の担当者。パスの外で見ることが多い |
| 時間の範囲 | いま（数秒〜数分） | 長い期間（数日〜数か月） |
| コマンド | 画面のすぐそばでコマンドを送り、承認する | 見るだけ |
| 見るもの | モード、電源、アラーム、コマンドの結果 | バッテリーの電圧の傾き、信号の強さの移り変わり、パスどうしの比べ |

**運用画面の作り方の考え方**

- **1枚で判断できる**：パスの間に他の画面を探していては間に合わない。次のコマンドを決めるのに要る値を、1枚に集める
- **色で気づける**：数字を読まなくても、モードやアラームが色でわかるようにする
- **古い値に気づける**：通信が途切れても、最後の値はそのまま表示されている。いつ届いた値なのかがわからないと、止まった衛星を元気だと思い込んでしまう。そのため、決まった時間届かなかった値は「期限切れ」として目立たせる
- **画面からコマンドを送るときも、安全装置は同じ**：ボタンから送っても、送信の前提条件や承認の待ち行列は、送信画面から送るときと同じように働く

トレンドの監視は、運用画面では気づけない、ゆっくりした変化（電池の劣化、部品の温度がだんだん上がる など）を見つけるためのものです。

<a id="hosted-payload"></a>

## 12. 複数の会社のペイロードを載せる

1機の衛星に複数のペイロードが載り、それぞれ別の会社が使うことがあります。他社の衛星に自社の機器を相乗りさせる形は、ホステッドペイロードと呼ばれます。このとき、**データは会社ごとに分けたいけれど、衛星の運用は分けてはいけない** という事情があります。

**データを分けたい理由**

各社にとって、自社のペイロードのデータは商品や研究の成果そのものです。他社に見せたくありませんし、他社のデータを見る必要もありません。

**衛星の運用を分けてはいけない理由**

ペイロードの操作も、バス（衛星本体）の資源を使います。

| 資源 | ぶつかる例 |
| --- | --- |
| 電力 | 2つのペイロードを同時に ON にすると、電力が足りなくなる |
| 姿勢 | A社はカメラを地上へ向けたいが、B社はアンテナを別の方向へ向けたい |
| 安全 | ペイロードのコマンドを送ってよいかは、バスの状態で決まる。M5Sat の「SAFE のときはペイロードを操作しない」（5-5の送信の前提条件）も、バスの運用モードを見ている |
| 通信の時間 | パスの短い時間を、各社のデータを降ろす時間とコマンドを送る時間で分け合う |

各社が別々のシステムから直接コマンドを送ると、この調整と安全の確認ができません。そのため、最終的な判断と送信はバスの運用者が一手に持ちます。

**よくある分け方**

| 役割 | 持っているもの |
| --- | --- |
| バスの運用者（管制） | 衛星全体の定義（MDB）、全部のテレメトリ、送信の権限、パスの計画 |
| ペイロードの会社（ペイロード運用センター） | 自社のペイロードのデータ。コマンドは要求として出し、管制が確かめてから送る |

ペイロードの会社がその場でコマンドを打つことは少なく、多くは次のどちらかです。

- 「この時間にこの観測をしたい」という要求を出し、管制が運用の計画に組み込む（[7. 時刻指定の運用と観測の計画](#planning)）
- 観測したデータを、地上へ降ろしたあとにファイルで受け取る

**YAMCS で作るなら**

| 作り方 | 中身 | 向き・不向き |
| --- | --- | --- |
| 1つのインスタンスで、権限を分ける | ユーザーを「バスの運用者」と「各社の担当」に分ける。パラメータやコマンドの名前の範囲ごとに、見てよい・送ってよいを決める（例：A社は `/M5Sat/PayloadA/.*` だけ）。各社の担当が送ったコマンドは、承認の待ち行列でバスの運用者が承認してから送る | YAMCS がもともと持つ仕組みで作れる。データの保管場所は1つなので、分け方は権限だけに頼る |
| ペイロード用のインスタンスを別に立てる | 管制のインスタンスで全部を受け、そのペイロードのパケット（APID）だけを各社のインスタンスへ渡す。各社のコマンドは管制のインスタンスを通してから衛星へ送る | データ・設定・アーカイブまで会社ごとに完全に分かれる。インスタンスどうしのつなぎ方を作る手間がかかる |

どちらの作り方でも、衛星へ送る出口は管制のインスタンス1つだけにします。M5Sat で試すかどうかは [issue #31](https://github.com/vestige/m5stack-yamcs/issues/31) で検討します。

<a id="ground-stations"></a>

## 13. 地上局とパス

**パスと AOS / LOS**

低軌道の衛星は、地上局から見える時間（パス）が1回あたり十数分ほどしかありません。衛星が見え始めることを AOS（Acquisition of Signal）、見えなくなることを LOS（Loss of Signal）と呼びます。M5Sat では、地上局の無線機（M5StickC）の画面にこれを出しています。M5Stack を持って離れると、本物のパスの終わりと同じように LOS になります。

**パスの予測と計画**

パスの時刻は、衛星の軌道（TLE などの軌道要素）と地上局の場所から計算します。地上局から見て、衛星が地平線より上（例：仰角5〜10°以上）にある時間帯がパスです。何日も先まで予測できるので、運用者は使うパスを選んで地上局を予約し、パスごとにやることを計画します。M5Sat は軌道を回っていないので、決まった間隔の人工のパスで代わりにしています（`tools/plan_passes.py`）。

パスの間にやることは、多くの場合、決まった順番になります。

1. AOS：衛星の信号をつかむ
2. 衛星の状態（HK）を確かめる。前のパスから何が起きたかを確かめる
3. 記録しておいたデータを降ろす（ダンプ）
4. 次のパスまでに衛星にやってほしいこと（観測の予約など）を送る
5. LOS

M5Sat では、1 と 2 を Timeline のアクティビティで自動にしています（AOS のあとに `01-link-check.ycs`）。

**通信できない間に起きたことを知る**

パスとパスの間、衛星は地上と話せないまま動き続けます。その間に起きたことを知るために、本物の衛星は覚えておくものの性質によって置き場所を使い分けています。

| 置き場所 | 大きさ | 再起動すると | 何を置くか | M5Sat では |
| --- | --- | --- | --- | --- |
| RAM | 小さい | 消える | 今の状態、カウンタ、最後の結果 | 運用モード、コマンドの数、最後の観測の結果 |
| 不揮発メモリ（EEPROM、フラッシュ、MRAM など） | 小さい | 残る | 再起動の回数、設定、失いたくない値 | 再起動の回数、回線の設定（NVS） |
| データレコーダ（大容量の記録装置） | GB〜TB | 残る | 観測データ、通信できない間の HK やイベント（あとでダンプする） | なし（[issue #34](https://github.com/vestige/m5stack-yamcs/issues/34)） |

「最後に何をして、どうなったか」を HK に入れておくのは、小さく作れてよく使われるやり方です。イベントは通信できない間に出ると届きませんが、HK は毎回送るので、次のパスで必ず目に入ります。

**場所の事情と複数の回線**

本物の衛星も、指令用・データ用など複数の回線を持ち、YAMCS ではそれぞれを別のデータリンクとして扱います。M5Sat でも、Wi-Fi のアクセスポイントに頼る回線（UDP）がクライアント分離の場所で使えなかったため、アクセスポイントを使わない ESP-NOW の回線（地上局の無線機）を足しました。

**複数の地上局とハンドオーバー**

本物の運用では、1機の衛星を世界のあちこちの地上局で順番に追いかけて、通信できる時間を増やします。衛星が地上局 A から地上局 B の見える範囲へ移るとき、通信する局を切り替えます（ハンドオーバー）。YAMCS でこれをどう扱うかは、[issue #19](https://github.com/vestige/m5stack-yamcs/issues/19) で調べる予定です。
